## 一、背景

老师在 `docs/` 下发了三个 `.doc` 模板（`assignment.doc` 任务书、`report-template.doc` 项目报告模板、
`meeting-minutes-template.doc` 会议记录模板）。任务书《提交材料》原文要求「**所有 doc 文档同时另存为
pdf 文档**」——语序表明 **doc 是主稿、PDF 是从稿**，老师给 `.doc` 模板的意图是「在这个文件里写」。

原实现把 `docs/report-template.doc` 当作「八章结构清单」，用 md + pandoc 复刻结构：`tools/make_pdf.py`
的 `md_to_docx()` 只是一句 `pandoc <md> -o <out.docx>`（`make_pdf.py:151-157`），**未传 `--reference-doc`**，
因此没有继承模板样式。实测 `deliverables/docx/00-项目报告.docx`：16 个表格虽转为真 docx 表格，但
**查不到任何 TOC 域**，也没有模板封面版式与页眉页脚域。

同时 `deliverables/00-项目报告.md` 是把 01–06 剪贴成「摘要表 + `> 完整内容见 XXX.md` 跳转链接」的汇编稿
（434 行中 136 行为表格、无序列表 7 条、有序列表 9 条、**mermaid 0 处**），并在 §2/§3/§5/§7 各挂一句
「完整内容见 …」把正文外包，读起来是索引而非报告。

## 二、选项对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| (a) 维持现状（md → pandoc → docx/PDF） | 不动已跑通的产线 | 版式与老师模板不一致；报告退化为摘要+外链；目录域缺失；无 mermaid 图形能力 |
| **(b) 在老师模板 docx 上原地填内容，六份合一，只交一份报告** | 版式 100% 与模板一致；目录/页眉页脚域天然正确；无重复交付 | 需新增构建脚本与图源；报告正文需按模板重写一遍 |
| (c) 六份独立文档 + 一份报告 | 形式上对齐「验收依据」的枚举 | 与老师下发模板的本意不符；同一内容重复交付三遍（md/docx/pdf） |

## 三、结论

**采用 (b)。**

1. **新增 `submission/` 作为唯一提交材料目录**，结构照任务书《提交材料》排：
   `00-项目报告.docx`、`00-项目报告.pdf`、`readme.txt`、`会议记录/`、`个人任务及感想/`、`演示视频/`。
   **`deliverables/` 保持原始样子**——不整理、不归档、不删改（组长明确要求）。
2. **报告 = 六份合一**：01–06 退出交付清单，仅作内容来源。报告按老师模板八章组织：
   1 软硬件环境 / 2 需求分析 / 3 详细设计（3.1 类设计、3.2 核心流程描述、3.3 核心算法设计）/
   4 运行结果截图 / 5 测试（测试用例设计、运行结果）/ 6 系统特色以及可扩展点 / 7 感想 / 8 附件（会议记录），
   前置封面、分工描述表、修订历史记录表、目录。
3. **责任边界**：构建脚本产出 `submission/00-项目报告.docx`；**PDF 由组长在 Word 中导出**
   （Word 会按真实分页重算 `TOC` 域，规避「用 HTML 后端猜页码」的风险，原计划的
   `refresh + 两遍法 + pdftotext 反查`整段作废）。
4. **打包仍由 CI 完成**：`.github/workflows/deliverables.yml` 不变，仅 `tools/package_deliverables.py`
   改为按 `submission/` 收材料，产物 `group01.zip` → GitHub Release。

## 四、理由

1. **符合老师的交付意图**：模板是 `.doc`，交付形态应是「doc 主稿 + PDF 另存」，而不是反向让模板来迁就 md。
2. **版式零风险**：在模板副本上原地填内容，样式（`标题`/`标题 1`/`标题 2`/`目录 1`/`Tabletext`）、
   页眉页脚域、页面尺寸（21.59×27.94 cm）全部天然继承，不存在「转换失真」。
3. **消除重复交付**：同一内容此前以 md / docx / pdf 三种载体各交一遍，且报告与 05-测试报告存在
   用例表、性能表、缺陷表的系统性重复。合并后只交一份。
4. **目录页码正确性由 Word 保证**：`officecli refresh` 在 macOS 上可跑（回退 `backend: html`，
   实测能把目录页码从 5 改为 4 且保留 `PAGEREF` 域），可作为预填；最终以 Word 重算为准。

## 五、技术可行性（已实测）

| 环节 | 工具 | 实测结果 |
|---|---|---|
| `.doc → .docx` | ONLYOFFICE 自带 `x2t`（`/Applications/ONLYOFFICE.app/Contents/Resources/converter/x2t`） | 成功，产物 26 KB |
| 读取/填充模板 | `officecli` 1.0.145（`~/.local/bin/officecli`） | 段落、样式名、图片（`--prop width=6cm`，**必须带单位**）、表格（`colspan`/`vmerge`）、分页、页眉页脚、`field`(PAGE/NUMPAGES)、`toc`、`hyperlink` 全部支持 |

## 七、实施中发现并留档的技术要点

1. **`officecli refresh` 会破坏目录格式，不要用**。实测它能把页码算对（回退 HTML 后端），
   但重建目录条目时丢掉了「1.」编号前缀与点线前导符，条目退化成 `软硬件环境4`。
   改用标准做法：在 `settings.xml` 里置 `<w:updateFields w:val="true"/>`（位置必须在
   `w:footnotePr` 之前，否则触发 schema 错误），Word 打开时会自行重算目录与页码域。
   实现见 `tools/build_report.py` 的 `Oc.set_update_fields()`，`--refresh` 仅作诊断保留。
2. **`.doc → .docx` 需要 `x2t`**（ONLYOFFICE 自带：
   `/Applications/ONLYOFFICE.app/Contents/Resources/converter/x2t`）。转出的模板已提交为
   `report/template.docx`，因此构建不再依赖本机是否装了 ONLYOFFICE。
3. **图的可读性由「PNG 像素宽」决定，而不是「H/W 比」**。图按 16cm 插入 A4 竖版时：
   `页面字号(pt) ≈ 图中字号(px) × 453.5 / PNG宽度(px)`。只限制纵横比会把图拉成
   4000+ px 宽的扁条，字落到页面上不足 2pt。因此判据是 **PNG 宽 ≤ 约 1800 px**
   （即图中字号与画布宽度之比 ≥ 1:57），配套要求 H/W ≤ 1.2，实现见
   `tools/gen_diagrams.py`（按 SVG 实测尺寸定画布，另设最小画布高 260 CSS px，
   以避开“过扁的图被截成细条”的坑）。
   ⚠️ 这一条还有个前提：**画布尺寸对 ≠ 内容真的铺满画布**。踩过的坑见第 7 条。
4. **`officecli` 会给每个文件路径起常驻进程**，上一次运行的常驻会用内存里的旧文档
   覆盖刚拷进来的模板（实测把 11 行的分工表变成 6 行）。故 `build_report.py` 在拷模板前
   先对目标路径执行 `close`。
5. **表格列宽要按内容比例分配**：不给 `colWidths` 只能建出单列表格；给等宽则长文本列被挤成
   窄条、编号列被挤成两行。实现见 `tools/build_report.py` 的 `auto_col_widths()`。
6. **打包脚本会自动先跑 `build_submission.py`**：CI 的步骤里没有单独跑它，若不自动调，
   CI 会拿仓库里已有的旧副本进包，与本机刷新结果不一致。
7. **「画布尺寸对」不等于「图能看清」：mermaid stateDiagram 的 svg 没有显式尺寸。**
   实测（组长在 docx 里发现图 3-3 小到看不清，回溯到渲染链路）：

   - mermaid 对 `stateDiagram-v2` 生成的 svg 是 `<svg width="100%"
     style="max-width: 1036.76px" viewBox="0 0 1036.76 219">`——**只给宽度百分比，不给 height**；
   - 按 CSS 规范，缺省尺寸的替换元素（replaced element）取**默认对象尺寸 300×150**，
     于是 Chrome 把它渲染成 300×63.36 CSS px（`getBoundingClientRect()` 实测），
     内容被缩到 `300 / 1036.76 = 28.9%`：`g.nodes` 的 bbox 是 1021 用户单位，
     渲染后只有 295 CSS px —— 与 PNG 里量到的墨迹 592×115 设备 px 完全吻合；
   - 而 `measure()` 是按 svg 的 **viewBox** 开截图窗口的（1084×267 CSS），
     于是 PNG 画布 2168×534 尺寸完全正确、内容却只占左上角 **27%×22%**，
     摆到 16cm 宽时图内字号仅约 **4.6pt**（同批 4 张 flowchart 的墨迹占宽 93~94%，约 7.4~8.5pt）。
   - 注意 `svg.getBBox()` **查不出**这个问题（它返回 1021×175，说内容铺满了画布），
     因为图里确实有无形元素撑满 viewBox；必须**扫像素**才能发现。

   修法与守门（均已落地）：
   1) `tools/gen_diagrams.py` 渲染后注入 JS：svg 的 width/height 不是数字时，按 viewBox
      回填显式尺寸（`svg 盒子 = 内容尺寸`，1:1）；已有显式尺寸的 flowchart 不受影响
      （重渲后 4 张流程图 PNG 的 SHA256 与改前**逐字节相同**）；
   2) 新增 `tools/png_ink.py`（纯标准库 zlib 解码 + 逐行反滤波，零依赖），截图后断言
      **墨迹宽度 ≥ 画布宽度 70%**，不达标直接非 0 退出并打印可操作提示；
   3) `tools/check_report.py` 对**成品 docx 里的 `word/media/*`** 做同一断言，
      把这次的事故类型固化成了机械验收项（当前实测能精准指出 `word/media/image5.png`）。
