## 一、背景

Issue #8 要求产出三端单文件产物、`tools/build.py` 统一入口、空目录启动冒烟、`readme.txt`
与体积数据留档。本机环境：Ubuntu 24.04 / x86_64 / Python 3.11.16 / PySide6 6.11.2，
`uv.lock` 已锁定 pyinstaller 6.22.3（dev 组）。

首次构建（未做任何体积优化）即得 **72,257,448 字节（68.9 MB）**，与「首次启动慢」

## 二、决策 1：打包器维持 PyInstaller，**不**换 Nuitka

### 选项

| 选项 | 说明 |
|---|---|
| A. 维持 PyInstaller（采纳） | 沿用 Issue #1 定案；已在 CI 跑通 |
| B. 换 Nuitka | 需新开 issue + `uv add nuitka` |

### 结论与理由（A）

1. **已定案**：`2026-09-15-技术栈定案.md` + Issue #1 已定 PyInstaller；按 TOP RULE，
   换栈必须先开 issue。
2. **依赖红线**：`pyinstaller` 已在 `uv.lock` dev 组；Nuitka **不在锁文件内**，换栈等于
   新增依赖，触碰 AGENTS.md「新增依赖须 `uv add` 并开 issue」的红线。
3. **CI 已在用**：`.github/workflows/ci.yml` 的 `build-windows-exe` 用 PyInstaller 且为绿；
   换栈要重写 Windows 流水线。
4. **Nuitka 的成本与本项目硬性要求冲突**（依据 Nuitka 官方文档 `user-documentation/tips.html`）：
   - 需要每端 C 工具链（gcc / MSVC / MinGW64 / clang-cl），并建议 `ccache`；
     macOS arm64 还需经 Homebrew 装 ccache。
   - Windows 独立程序**依赖目标机 VC 运行时**（"the standalone programs have external
     dependencies to Visual C Runtime libraries"），旧系统还需装 redist。
   - Windows Defender / 索引服务会在编译期锁文件导致**随机构建失败**
     （"preventing operations randomly due to holding locks"）。
   - 文档明示 Qt 插件需 `--enable-plugin=pyside6`；且 Nuitka **不设 `sys.frozen`**，
     改用 `__compiled__`，与现有代码/测试的冻结判断口径不同。
   以上每一条都削弱「空目录（无 Python 环境）可运行」与三端矩阵的确定性。
5. **Nuitka 的优势对本作业无效**：体积小、启动快、代码保护——但交付 zip 明确包含源码
   （见 `readme.txt` 第六节），保护无意义；体积问题用 `--strip` 与后续插件裁剪解决更省事。
   且 M4 截止 9.26–27，Nuitka 的 C 编译耗时（需缓存才可接受）不划算。

### 风险与对策（沿用定案）

| 风险 | 对策 |
|---|---|
| Windows 杀软误报 | 用 GitHub Actions 官方环境产物 + 附 SHA256（已写入 `readme.txt` FAQ Q1） |
| 单文件首次启动慢（需解压） | 文档写明并建议演示前预热（`readme.txt` FAQ Q2） |

## 三、决策 2：`--exclude-module` 保留但**不作为体积杠杆**（实测收益 ≈ 0）

`tools/build.py` 内置 51 项 Qt + 13 项 Python 排除清单。实测对照（同机、连续构建）：

| 配置 | 字节 | MB |
|---|---|---|
| 关排除（`--no-optimize`） | 72,257,448 | 68.9 |
| 开排除 | 72,258,160 | 68.9 |
| **差值** | **+712 B** | 属构建噪声 |

**结论：收益为 0，不是优化手段。** 原因（已核对 PyInstaller 源码）：
`PyInstaller/hooks/hook-PySide6.*.py` 走 `add_qt6_dependencies(__file__)`，即
**按「被 import 的 Qt 模块」**收集库与插件——`app/` 只 import 了
`QtCore / QtGui / QtWidgets`（`grep -rh "^from PySide6" app/` 可复核），未 import 的
Qt 模块本来就不会进包，排除它自然不省体积。

**保留清单的用途**：① 意图可复核；② 兜住日后 hook 行为变化或新增 hiddenimport。
已在脚本注释中同步标注「实测收益≈0」，避免后人误当成体积杠杆。

## 四、决策 3：开启 `--strip`（唯一有效的安全杠杆）

`libpython3.11.so.1.0` 在 uv 的 CPython 构建里**未 strip**（`file` 实测 "not stripped"，
解压后 20.77 MB），而 PySide6 的 Qt 库本身已 stripped。

| 配置 | 字节 | 相对基线 |
|---|---|---|
| 排除开 + strip 关 | 72,258,160 | — |
| 排除开 + **strip 开** | **71,363,616** | **−894,544 B（−0.85 MB）** |

- 采纳：`tools/build.py` 默认在 \*NIX 开启 `--strip`，Windows 默认关闭
  （PyInstaller 官方文档标注 `-s/--strip` "not recommended for Windows"）。
- 优化后产物**仍通过空目录启动冒烟**（见第五节）。
- 最终 Linux 产物：**71,363,616 字节（68.1 MB）**，构建耗时 29.7 s。

## 五、空目录启动冒烟：判据与结果

`tools/build.py --smoke` 实现。做法：把产物**单独拷进临时空目录**，以白名单环境变量启动
（只给 `PATH` / `QT_QPA_PLATFORM=offscreen` / `LANG`，**剥离** `PYTHONPATH`、`PYTHONHOME`、
`VIRTUAL_ENV`、`LD_LIBRARY_PATH`，等价 `env -i`），`cwd` 设为该空目录。

**判据（两条都满足才过）**：
1. 进程启动后至少存活 10 s 不退出（GUI 程序进事件循环本就不该自行退出；提前非 0 退出 = 启动即崩）；
2. 这 10 s 内 stderr 未出现 `Traceback` / `ModuleNotFoundError` / `ImportError` /
   `cannot open shared object file` / `could not load the Qt platform plugin` 等失败标记。

**刻意不改 `app/` 代码**去加自检开关——交付物里不该埋「自动退出」后门。因此判据是
「存活 + 无异常」而非「自证渲染完成」，此局限如实记录。

**结果（Linux）**：存活 10 s ✓；stderr 仅有 `This plugin does not support propagateSizeHints()`
（offscreen 平台的已知无害提示）；**通过**。另用静态佐证：产物字节流中命中
`libqxcb.so`、`libqoffscreen.so`（平台插件确实已内嵌）。

### 5.1 追加证据：真实 X11 桌面（xcb）路径验证

本机存在**真实 X11 会话**（`DISPLAY=:1`，1920x1080，`XDG_SESSION_TYPE=x11`），
因此除 offscreen 冒烟外，另做了真实桌面路径验证——**不设** `QT_QPA_PLATFORM`，
即让 Qt 走 `libqxcb.so`：

| 检查项 | 实测结果 |
|---|---|
| 运行方式 | 产物拷进空目录 `/tmp/frozen-xcb/` 后直接执行 |
| 窗口是否出现 | `xwininfo` 命中 `"TopoSort — 拓扑排序演示"` 1280x800（mutter 装饰框 1308x866+36+70） |
| 进程稳定性 | onefile 父子两进程（429945 / 429965）持续存活 |
| **stderr** | **整个会话完全为空（零报错）** |
| 截图存档 | `evidence/screenshots/打包产物运行-20260921-1.png`（1280x788，48.8 KB） |

这一条比 offscreen 冒烟强得多：它**真正加载了 `libqxcb.so` 及其依赖链**
（X11 / xcb / dbus / GL / fontconfig 等），证明包内二进制依赖完整，
而不只是「进程没崩」。

## 六、决策 4：Qt 插件裁剪 —— **评估后否决，转为待办**

体积构成实测（解压后，取自产物归档 TOC；共 301 条，解压合计 180.3 MB / 压缩后 68.8 MB）：

| 条目 | 解压 MB | 谁拖进来的 |
|---|---|---|
| `PySide6/Qt/lib/libicudata.so.73` | 30.55 | libQt6Core 硬依赖 → **不可裁** |
| `libpython3.11.so.1.0` | 20.77 | 解释器本体 → **不可裁**（已 strip） |
| `PySide6/Qt/lib/libQt6Gui.so.6` | 10.88 | 使用中 |
| `PySide6/Qt/lib/libQt6Quick.so.6` | 7.89 | **`platforminputcontexts/libqtvirtualkeyboardplugin.so`** |
| `libgtk-3.so.0` | 7.78 | **`platformthemes/libqgtk3.so`** |
| `PySide6/Qt/lib/libQt6Widgets.so.6` | 7.78 | 使用中 |
| `PySide6/Qt/lib/libQt6Core.so.6` | 7.18 | 使用中 |
| `PySide6/Qt/lib/libQt6Qml.so.6` | 6.47 | 同上（虚拟键盘是 QML 实现） |
| `PySide6/QtWidgets.abi3.so` | 5.82 | 使用中 |
| `libcrypto.so.3` | 5.06 | **`tls/libqopensslbackend.so`** |
| `PySide6/Qt/lib/libQt6Pdf.so.6` | 4.30 | **`imageformats/libqpdf.so`** |

另收录 57 个 Qt 插件，含 `platforms/libqeglfs`、`libqlinuxfb`、`libqvnc`、`generic/libqevdev*`
等桌面场景根本用不到的项。

**诱人的裁法**：删掉 `libqgtk3` + `libqtvirtualkeyboardplugin` + `libqpdf` + TLS 插件，
理论上可省约 40 MB（解压后）。**但否决**，理由：

1. **`--exclude-module` 管不到插件**：插件是经「二进制依赖分析」收进来的，只能删
   `a.binaries`（需改用 spec 文件）或在 hook 阶段拦截。
2. **删插件不会自动删孤儿库**：`Analysis` 的依赖遍历发生在收集之后，删掉插件后
   `libgtk-3`、`libQt6Quick` 等仍留在 `a.binaries` 里，必须**手工列出传递闭包**。
3. **手工清单一定会错——已实测证伪**：直觉上「GTK 系」可裁，但 `ldd` 实测
   `libglib-2.0.so.0`、`libgthread-2.0.so.0`、`libpcre2-8.so.0` 是
   **libQt6Core/Gui/Widgets 的直接依赖**；`libgcrypt.so.20`、`libgpg-error.so.0` 是
   **libQt6Gui/Widgets/libqxcb 的直接依赖**。照直觉裁这两个必然启动即崩。
4. **裁剪手段会污染三端**：正确做法是写自定义 hook 覆盖
   `hook-PySide6.QtGui/QtWidgets`，在 `add_qt6_dependencies` 之后、依赖遍历之前过滤插件。
   该 hook 会**同样作用于 Windows 与 macOS**，而本机只能验证 Linux（无 Windows/macOS
   环境）。拿一套只能在 1/3 平台上验证的 hook 去换约 20 MB，与 Issue #8
   「三端产物各自通过启动冒烟」的验收方向相反。
5. **验证能力已具备，但不足以翻案**：本机确实有真实 X11 会话（`DISPLAY=:1`，见 5.1 节），
   所以 Linux 侧 xcb 路径**可以**验证（本次已用该方法验证了未裁剪产物）；
   但第 4 条的跨平台不可验证问题、以及第 2、3 条的传递闭包问题依然存在。

**转为待办（建议新开 issue）**：若确需瘦身，正确做法是
① 写自定义 hook 覆盖 `hook-PySide6.QtGui/QtWidgets`，在 `add_qt6_dependencies` 之后、
依赖遍历之前过滤插件；② 用 `--onedir` 物化文件后 `ldd` 全量核验无悬空依赖；
③ 在真实 X11（本机 `DISPLAY=:1`）下以 `QT_QPA_PLATFORM=xcb` 冒烟并截图，
确认 stderr 为空后再交付；④ **必须在 Windows CI 上重新验证**该 hook 不破坏 Windows 产物。
候选清单：`platformthemes/libqgtk3`、`platforminputcontexts/libqtvirtualkeyboardplugin`、
`imageformats/libqpdf`、`imageformats/libqsvg`、`iconengines/libqsvgicon`、
`tls/libqopensslbackend`、`tls/libqcertonlybackend`、`networkinformation/libq*`、
`platforms/libq{eglfs,linuxfb,minimalegl,vnc,vkkhrdisplay}`、`egldeviceintegrations/*`、
`generic/libqevdev*`、`generic/libqtuiotouchplugin`。
**必须保留**：`platforms/libq{xcb,wayland,offscreen,minimal}`、`libglib-2.0`、
`libgthread-2.0`、`libpcre2-8`、`libgcrypt`、`libgpg-error`、`libicudata`、`libpython`。
