## 二、决策

### 决策 1：单独开 `release.yml`，不塞进 `ci.yml`

- `ci.yml` 的职责是「代码对不对」（契约测试 + 机械红线），触发条件含 PR。
- `release.yml` 的职责是「产物能不能交付」，需要 `contents: write` 权限。
- 把发布权限给每个 PR 是不必要的放大；两者触发条件与权限需求都不同，故分离。

### 决策 2：用 runner 自带的 `gh` CLI，不引入第三方 release Action

- AGENTS.md 规定新增依赖须先讨论留档。
- `gh` 已预装在三类 runner 上 ⇒ **零新增依赖**。
- 用到的 `actions/checkout`、`actions/upload-artifact`、`actions/download-artifact`
  均为 GitHub 官方 Action，且前两个 `ci.yml` 已在用。
- 对比：常见做法是 `softprops/action-gh-release` 等第三方 Action，但那会引入外部维护者
  依赖，与本项目「依赖只从 pyproject/uv.lock 走」的纪律不一致。

### 决策 3：三份产物都在 CI 构建（含 macOS）

- 单文件产物无法跨平台交叉打包，三端必须各自在本平台构建。
- 用 `ubuntu-latest` / `macos-latest` / `windows-latest` 三矩阵项，
  各自执行**同一条命令** `uv run python tools/build.py --smoke`。
- 收益：**补齐了此前缺失的 macOS 产物**（Issue #8 中「macOS 未构建」一项由此闭环），
  且 Windows 产物名从 `main.exe` 修正为 `TopoSort.exe`（CI 迁移到 build.py 的副产品）。

### 决策 4：macOS 必须用 onedir（PyInstaller 已弃用 onefile+windowed）

**这是本次调查最重要的发现**，依据 PyInstaller 6.22 源码：

```
PyInstaller/building/osx.py:33
WINDOWED_ONEFILE_DEPRCATION = (
    "Onefile mode in combination with macOS .app bundles (windowed mode) don't make sense
     (a .app bundle can not be a single file) and clashes with macOS's security.
     Please migrate to onedir mode. This will become an error in v7.0."
)
```
触发点：`PyInstaller/building/makespec.py:745`（`if is_darwin and onefile and not console`）。

→ `tools/build.py` 新增 `--mode`，默认 **macOS=onedir、其余=onefile**。
Linux/Windows 仍保持单文件（技术栈定案要求「单二进制双击即跑」）。

配套证据（同一份源码）：

| 事实 | 证据位置 |
|---|---|
| macOS 上 onefile 与 onedir 都会额外产出 `.app` | `makespec.py:863-873`（`bundleexetmplt` / `bundletmplt`） |
| `.app` 是**自包含**的：BUNDLE 用 `shutil.copyfile` 把文件拷进 `Contents/Frameworks`，仅 `SYMLINK` 类型才建软链 | `osx.py:657-700` |
| strip 与 codesign 由同一个 `process_collected_binary` 处理（**先 strip 后签名**），之后 BUNDLE 还会 `sign_binary(deep=True)` 重签 | `api.py:315-319`、`osx.py:697-699` |

→ 因为 `.app` 自包含，**只把 `.app` 打成 zip 即可分发**，不需要同级 onedir 目录。

### 决策 5：用 `ditto` 打 macOS zip，不用 Python `zipfile`

`.app` 内含 **103 个符号链接**（Qt framework 的 `Versions/Current → A` 等）。
Python 标准库 `zipfile` **不保留符号链接**，用它打包会产出缺 103 个链接的坏包。
`ditto -c -k --sequesterRsrc --keepParent` 是 macOS 自带工具，能正确保留链接与权限，
且不引入新依赖。已在 T7 验证阶段逐条解析确认 103 个链接全部可解析到包内实体。

### 决策 6：发布前先自检，且校验值随产物发布

- `release` job 在创建 Release 前先 `sha256sum -c ./*.sha256`，**下载回来的产物必须先自证一致**。
- `tools/build.py` 每次构建都生成 `<交付物>.sha256`（`sha256sum -c` 兼容格式）。
- 理由：**PyInstaller 产物不是字节可复现的**。本机用完全相同参数连续构建三次：
  `71,363,616` / `71,363,600` / `71,363,768` 字节，三个不同哈希
  （PyInstaller 的 `SOURCE_DATE_EPOCH` 只在 `api.py:877-879` 的 Windows 分支生效，
  改的是 PE 时间戳，救不了 Linux/macOS）。
  所以校验值只能「这次构建配这次发布」，不能写死在文档里当固定值。

### 决策 7：tag 方案 `v*`，本次用 `v0.1.0`

- `on: push: tags: ['v*']` + `workflow_dispatch`。
- 版本号与 `pyproject.toml` 的 `version = "0.1.0"` 对齐。
- `workflow_dispatch` 用于**打 tag 前预演**：只构建不发版（`release` job 有
  `if: startsWith(github.ref, 'refs/tags/')` 守卫）。
- 已知限制：`workflow_dispatch` 要求 workflow **已存在于默认分支**，
  否则报 `HTTP 404: workflow release.yml not found on the default branch`。
  因此实际顺序是「先合入 master → 在 master 上 dispatch 预演 → 再打 tag」。

## 三、实测结果

### 3.1 三份产物（Release v0.1.0，run 35620768539）

| 平台 | 产物 | 体积 | SHA256 | 模式 | 打包耗时 |
|---|---|---|---|---|---|
| Linux | `TopoSort` | 67,121,240 B (64.0 MB) | `4b01313c0fd21c929e1350f57cf3aa7637cfbb0046c8ab38e77b6ad82567daf9` | onefile | 38.8 s |
| Windows | `TopoSort.exe` | 48,753,119 B (46.5 MB) | `0691424b1ba2aa3157a6850a0b37dacebfef7adaf098272ff00021a042679ff4` | onefile | 68.2 s |
| macOS | `TopoSort-macos.zip` | 36,649,790 B (35.0 MB) | `d13b8d8eb4cd30337899050ec6537b114d4d1d379558593ed72641f8e619a4dc` | **onedir** + zip | 26.5 s |

### 3.3 三平台冒烟

`tools/build.py --smoke` 在三个 runner 上均通过（判据：offscreen 下存活 10 s 且 stderr
无失败标记）。offscreen 平台插件在三端都存在，依据：PyInstaller 的 Qt hook 是
**整目录收集**插件（`utils/hooks/qt/_modules_info.py:189-212` 的
`_QtModuleDef("QtGui", plugins=[..., "platforms", ...])`），而字符串 `offscreen`
在 PyInstaller 源码中**零出现**（即不是白名单）。

## 四、开发过程中发现并修复的 4 个问题

全部有 CI 日志证据，记录在此以免重蹈：

| # | 现象 | 根因 | 修复 | 证据 |
|---|---|---|---|---|
| 1 | Windows job 10 秒即退出，PyInstaller 根本没跑 | Windows 控制台默认 cp936/cp1252，脚本打印中文抛 `UnicodeEncodeError: 'charmap' codec can't encode` | 新增 `force_utf8_stdio()`，入口把 stdout/stderr `reconfigure` 成 UTF-8 + `errors="replace"`；smoke 子进程输出显式按 UTF-8 解码 | run 35617828612 |
| 2 | Windows 构建成功但 job 失败 | 被 `taskkill` 终止的进程短暂持有 exe 句柄，`TemporaryDirectory.__exit__` 删不掉目录抛 `PermissionError: [WinError 5]`，把「构建成功」变成「步骤失败」 | `ignore_cleanup_errors=True` + 终止后 1 s 宽限 | run 35618645820 |
| 3 | 三平台构建全成功，仅发布 job 失败 | 该 job 刻意不做 `actions/checkout`（只要产物不要源码），没有 `.git` 目录，`gh` 无法推断仓库 → `fatal: not a git repository` | job 级显式 `GH_REPO: ${{ github.repository }}` | run 35620024862 |
| 4 | 体积统计虚高：macOS `.app` 报 271.7 MB | `Path.rglob("*") + is_file()` 会**跟随符号链接**，同一实体被重复计入 | 统计时排除 `f.is_symlink()`；修正后真实值 96.9 MB | T7 验证阶段自查发现 |

问题 1–3 是「本地只能验 Linux」这一约束的直接代价——**只能靠 CI 迭代发现**，
这也是把三平台构建放进 CI 而不是只做本机构建的价值所在。
