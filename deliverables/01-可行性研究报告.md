## 1. 引言

### 1.1 编写目的

本文档回答一个问题：**这个拓扑排序应用软件，值不值得做、能不能做成、按什么方案做。**

它不是需求说明书，也不是设计文档——那两份分别是 `deliverables/02-需求分析.md` 与
`deliverables/03-概要设计.md`。本文只负责在动工前把"技术路线、算法难度、成本、
使用场景、时间排期、失败风险"六件事论证清楚，并给出**选型结论**，供后续文档引用。

### 1.2 项目背景

拓扑排序解决的是"有先后约束的任务如何排出一个合法顺序"这类问题：学生选课要满足
先修关系、汽车配件装配要满足工序依赖、复杂项目要满足任务依赖。当约束关系较多时，
人手工推算既慢又容易漏解——而很多情况下**合法顺序不止一种**，只看一条结果无法判断
排布空间有多大。

老师下发的任务书（`docs/assignment.doc`）要求：实现一个**桌面应用**（明确不能是
网页形式），输入先后关系、画出关系图、**用动画演示排序全过程**、给出尽可能多的
拓扑排序结果，并能识别约束自相矛盾的情况。

任务书同时给出了硬约束：**关键时间 9.14 布置 / 9.21 中期检查 / 9.28 打包提交现场验收**，
成绩 = 阶段性验收 40% + 整体性验收 60%；验收依据包含"设计文档完整性、原创性、
可运行、系统功能完整、代码规范、智能性"六项。

### 1.3 术语与缩写

| 术语 | 含义 |
|---|---|
| 拓扑序（topological order） | 把有向图全部节点排成一条序列，使每条边 `a→b` 都满足 a 排在 b 之前 |
| Kahn 算法 | 反复取"入度为 0"的节点输出并删除其出边，从而逐层消点；本项目用作动画演示的主线 |
| 全序枚举 | 枚举出**全部**合法拓扑序（本项目的核心考点之一） |
| 分层（layers） | 层号 = 从源点出发的最长路径长度，是拓扑排序的副产品，用于固定布局 |
| 泳道（lane） | 可视化概念：一条分支占一条横向泳道，用于展示"多路合法序并行推进" |
| onefile / onedir | PyInstaller 两种打包模式：单文件（运行时自解压）/ 目录（含 `.app` 包） |

## 3. 可行性分析

### 3.1 技术可行性

**结论：可行。** 关键技术风险在于"能否用有限的 GUI 库做出动态演化效果"，这一条
经过方案对比后已被化解。

#### 3.1.1 核心技术难点

本项目的技术难点**不是**拓扑排序本身，而是"**动画**"：

- 节点不是一次性画完就静止，而是要随算法推进**改变视觉状态**
  （待命 → 就绪 → 激活 → 幽灵消隐）；
- 分叉时会出现**多条分支同时推进**，需要"伪并发"的可视化表达（泳道）；
- 边要随节点消耗而淡化。

这意味着 GUI 框架必须提供**可控的、带时序的、针对图元的属性动画**，而不是
"重新计算布局并重绘整张图"。

#### 3.1.2 候选方案对比

| 候选方案 | 动态演化能力 | 三端能力 | 单文件打包 | 结论 |
|---|---|---|---|---|
| C# WinForms + MSAGL | 一般 | ❌ GViewer 仅 Windows | — | **淘汰**：无法覆盖三端目标 |
| C# Avalonia + AvaloniaGraphControl | ❌ 图重排无过渡动画，结构变更全量重建 | ✅ | ✅ 已实测 48 MB | **淘汰**：做不出动态演化效果 |
| Java + GraphStream | ✅ 动态图原生 | ✅ | ❌ jpackage 出文件夹非单文件 | **淘汰**：且力导向布局丢失分层语义 |
| **Python 3 + PySide6（QGraphicsView）** | ✅ QPropertyAnimation / QTimer 完全可控 | ✅ 原生支持 | ✅ PyInstaller | **采纳** |

#### 3.1.3 采纳理由：一个关键洞察

方案对比中出现了一个**决定性的洞察**：

> 本产品的可视化设计是"**固定分层布局 + 节点消耗渐隐**"，
> 而**不是**"力导向重排"。

这一区别让整件事变简单了：

1. **自动布局库不再必需**。分层布局的层号 = 从源点出发的最长路径长度，
   它是拓扑排序的副产品，自算 **≤40 行**。此前 Avalonia/GraphStream 方案之所以
   被淘汰，正是因为它们依赖"重排引擎"，而重排恰恰是我们不需要的。
2. **动画完全可控**。`QPropertyAnimation` + `QTimer` 提供逐帧可控的渐隐、脉冲、
   泳道分裂效果，且时长常量可集中管理（上界 1000 ms）。
3. **三端原生支持**。Python + PySide6 本身跨平台；打包按目标平台各自构建。
4. **迭代速度占优**。距提交约两周，Python 的开发效率是决定性优势。

#### 3.1.4 打包技术可行性

打包是"目标机无需 Python"这一目标的唯一实现路径，其可行性已实测验证：

| 验证项 | 结果 |
|---|---|
| Linux 单文件产物 | 71,363,616 字节（68.1 MB），构建耗时 29.7 s |
| 空目录启动冒烟（剥离 `PYTHONPATH`/`VIRTUAL_ENV`） | ✅ 存活 10 s，stderr 无失败标记 |
| 真实 X11 桌面（xcb）运行 | ✅ 窗口正常出现（1280×800），**stderr 全程为空** |
| Windows 产物 | ✅ 由 GitHub Actions `windows-latest` 产出（无本地 Windows 环境，必须走 CI） |
| macOS 产物 | ✅ 由 GitHub Actions `macos-latest` 产出为 `.app` 包 |
| 三端产物发布 | ✅ GitHub Release v0.1.0，每个产物附同名 `.sha256` |

其中"Windows 产物必须在 Windows 上打包"这一限制，通过 **CI 三平台矩阵**解决——
这不是妥协，而是把"无 Windows 开发机"这一约束转化为"每次提交自动验证三端"的优势。

### 3.2 算法可行性

**结论：可行，且是本项目的技术亮点。**

#### 3.2.1 三个算法各自的难度评估

| 算法 | 难度 | 可行性论证 |
|---|---|---|
| Kahn 拓扑排序 | 低 | 经典算法，O(V+E)，教科书级 |
| **全序枚举** | **中高** | 难点：不能只求一条序，要枚举**全部**；朴素递归会重复展开 |
| 环检测 | 低 | Kahn 的副产品：若剩余节点入度均 ≥1，则剩余节点即"环 ∪ 环下游" |

**全序枚举的实现思路已定案**：以 Kahn 步进为内核，维护**显式分支工作队列**——
某一步候选 frontier 有 k 个节点时，原分支按字典序选最小者继续，其余 k−1 个备选
**各开一条新分支**，且新分支首次推进必须消费其绑定时被分配的备选节点。
这样每条分支恰好对应一条合法序，不会重复也不会遗漏。详见
`evidence/decisions/2026-09-19-T3事件引擎设计定案.md`。

#### 3.2.2 正确性已被独立复核

算法实现过程中发现过一处**基准数据错误**，这个插曲反过来证明了算法正确：

- 既有契约把标准图 `<A,C> <A,E> <B,C> <C,D>` 的合法序数量记为 **6 条**；
- 实现输出 **7 条**，与基准冲突；
- 通过**独立穷举全部 5! = 120 个排列**复核，确认原清单**遗漏了合法序 `A E B C D`**，
  实现是对的；
- 最终**修正基准为 7 条**，而不是让算法去迁就错误的计数
  （见 `evidence/decisions/2026-09-18-标准图拓扑序数量修正.md`）。

这一决策体现了任务书要求的"智能性"——**算法不得为匹配错误计数而漏解**。

#### 3.2.3 规模风险及其防护

枚举全部拓扑序的最坏情况是**阶乘级**的。实测发现：30 节点双链图在逐拍交错调度下，
**26 秒零产出**——分支数按组合数爆炸。

防护措施（已实现并测试）：

1. **`max_completes` 截断参数**：累计完成数达到上限即停止推进，已得结果保留；
2. **前置保险丝**（终审发现的补充）：仅按"完成数"点火太晚，改为
   **Fork 前检查"已完成数 + 活跃分支数 ≥ max_completes 即不再开新分支"**，
   在爆炸发生前就掐断。

#### 3.2.4 确定性是可验收的性质

动画演示要"可复现"，就必须保证**同一输入的事件序列逐项相等**。这里有一个隐蔽陷阱：

> Python 的 `set` / `frozenset` 迭代顺序受 `PYTHONHASHSEED` 影响，
> **跨进程、跨平台不固定**。

若不处理，会在 CI 三平台上偶发翻红。对策已写入契约：**一切集合的遍历与事件发射
顺序一律 `sorted()` 字典序**。这条规则让"确定性"从"但愿如此"变成"可机械验收"，
并已通过 golden 事件流文件（`evidence/test-data/*.events.json`）锁定。

**没有采购、没有授权、没有服务器。** 唯一"成本"是 CI 的排队时间，实测三平台并行
构建耗时：Linux 72 s、Windows 108 s、macOS 65 s、发布 9 s（含 `uv sync` 与全量测试）。

**体积成本已实测并优化**（详见 `evidence/benchmarks.csv`）：

| 配置 | 字节 | 结论 |
|---|---|---|
| 基线（无优化） | 72,257,448 | 68.9 MB |
| 仅开 `--exclude-module` 排除清单 | 72,258,160 | **收益 ≈ 0（差 +712 B 属噪声）** |
| 排除 + `--strip` | **71,363,616** | **−894,544 B（−0.85 MB），唯一有效杠杆** |

排除清单收益为零的原因也已查清：PyInstaller 的 PySide6 hook 是**按"被 import 的
Qt 模块"**收集依赖的，`app/` 只 import 了 `QtCore/QtGui/QtWidgets`，未 import 的
模块本来就不会进包，排除它自然不省体积。这一"反直觉结论"已留档，避免后人重复劳动。

### 3.4 操作可行性

**结论：可行，且对使用者极为友好。**

1. **输入格式极简**：一行一条关系 `<a,b>`，西文尖括号。任务书统一规定了这一格式，
   我们在此基础上做了宽容处理（空白行跳过、全角 `（）` `，`、缺尖括号 `a,b` 也接受），
   降低手工输入门槛。
2. **目标机零依赖**：三端产物均为"双击即跑"，无需安装 Python 或任何库。
3. **获取路径清晰**：直接从 GitHub Release v0.1.0 下载对应平台产物，
   每个产物附 `.sha256` 校验文件；`readme.txt` 给出三端逐步操作说明与 FAQ。
4. **异常有明确指引**：文档覆盖了四类实际会遇到的拦路问题——
   Windows 杀软误报、单文件首次启动慢、Linux 缺 Qt 系统库、macOS 隔离属性，
   每类都给了具体命令或操作路径。
5. **演示友好**：提供调速、暂停、单步、跳完四个控制；动画节奏默认值经过调优
   （拍间隔默认 400 ms），保证课堂演示既不拖沓也不闪太快。

| 9 | **打包产物不可字节复现** | 低中 | 校验值随产物发布，不在文档里写死；文档明确警告 | ✅ 已解决 |
| 10 | **依赖安装源过慢** | 低 | 换清华源（实测 17.5 KB/s → 10.3 MB/s），并还原 lock 后提交 | ✅ 已解决 |
| 11 | **Qt 插件裁剪**（可省约 40 MB 解压体积） | 低 | **评估后主动否决**：需自定义 hook，会同时影响 Windows/macOS，而本机只能验证 Linux，风险收益不匹配 | ⏸ 转为待办 |
| 12 | **原创性/合规**（任务书要求不抄袭） | 高 | 算法全自研（红线）；不引入 networkx 等现成排序库；依赖仅 GUI/测试/打包三类，全部留档 | ✅ 已保证 |

其中第 11 条值得单独说明：Qt 插件裁剪表面上"能省 40 MB"，但正确做法需要写自定义
hook 覆盖 PyInstaller 内部的 `hook-PySide6.QtGui/QtWidgets`，而该 hook 会**同样作用于
Windows 与 macOS**——本机只能验证 Linux（无 Windows/macOS 环境）。用一套只能在
1/3 平台上验证的改动去换体积，与"三端产物各自通过启动冒烟"的验收方向相反，
因此**主动否决**，转为待办。这一判断记录在 `evidence/decisions/2026-09-21-打包发布方案.md` 第六节。

## 4. 方案对比与选型结论

### 4.1 已定案的选型

| 决策项 | 结论 | 依据 |
|---|---|---|
| 开发语言与 GUI | **Python 3 + PySide6（QGraphicsView）** | 动画可控 + 三端原生 + 迭代快 |
| 打包工具 | **PyInstaller** | 沿用定案；已在 CI 跑通；零新增依赖 |
| 打包模式 | Linux/Windows **onefile**；macOS **onedir** | macOS 的 onefile+windowed 已被 PyInstaller 弃用（v7.0 起报错） |
| 算法实现 | **全自研**（Kahn + 全序枚举 + 环检测） | 作业考点红线 |
| 工程管理 | **uv** | 依赖唯一入口，lock 可复现 |
| 发布方式 | **CI 三平台构建 → GitHub Release** | 无 Windows/macOS 开发机，CI 是唯一可行路径 |

### 4.2 被否决的方案及理由

| 方案 | 否决理由 |
|---|---|
| C# WinForms + MSAGL | GViewer 仅 Windows，无法覆盖三端目标 |
| C# Avalonia + AvaloniaGraphControl | 图重排无过渡动画、结构变更全量重建，做不出动态演化效果 |
| Java + GraphStream | jpackage 出文件夹非单文件；力导向布局丢失分层语义 |
| **Nuitka**（替换 PyInstaller） | 需每端 C 工具链；Windows 独立程序依赖目标机 VC 运行时；Defender/索引服务锁文件导致**随机构建失败**；不设 `sys.frozen` 与现有代码口径不符。且其优势（体积小/启动快/代码保护）对本作业**无效**——交付包明确包含源码，保护无意义 |
| Qt 插件裁剪 | 见 3.6 节第 11 条：跨平台不可验证，风险收益不匹配 |

## 5. 结论

1. **技术上可行。** 核心难点（动态演化动画）通过"固定分层布局 + 属性动画"这一
   关键洞察被化解，且已产出三端可运行产物。
2. **算法上可行且是亮点。** Kahn + 全序枚举 + 环检测全部自研；枚举正确性经独立
   穷举复核（并据此修正了基准数据）；阶乘级爆炸已由截断参数与前置保险丝防护。
3. **经济上可行。** 全栈开源，零采购、零授权、零服务器成本。
4. **操作上可行。** 输入格式极简，三端双击即跑，异常场景均有明确指引。
5. **进度上可行。** 核心开发与打包发布**均已提前完成**；契约先行与 CI 两层判定
   保证了并行开发不互相阻塞。剩余风险集中在文档收尾，已拆分为任务并指派到人。
6. **风险可控。** 12 项风险中 7 项已解决（含「原创性合规」这类已保证项）、
   3 项已缓解、1 项进行中（文档收尾）、1 项主动转为待办（Qt 插件裁剪），
   且全部有留档可追溯。

**综上，本项目具备完整可行性，建议按既定方案继续推进至 9.28 交付。**
