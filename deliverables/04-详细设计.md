## 1. 算法内核（models/）——T2 撰稿（本章定稿稿）

### 1.1 设计目标

算法内核位于 `app/models/`，负责关系文本解析、不可变图模型、环检测、

`Graph.nodes` 和 `Graph.edges` 使用 `frozenset`。算法运行时使用局部
邻接表、入度表和栈帧，不修改图对象，因此同一个 `Graph` 可被重复播放
并得到确定结果。

### 1.3 输入解析

解析器按物理行处理输入，空白行跳过。全角括号和逗号先规范化，再接受
以下三种形式：

```text
<A,B>
（A，B）
A,B
```

每个非空行必须恰好包含两个非空节点名。重复关系通过集合去重；
`<A,A>` 作为自环在解析阶段拒绝。格式错误抛出 `ParseError`，其中
`lineno` 从 1 开始，`line` 保留原始文本。

### 1.4 Kahn 图分析

预处理阶段由边集构造按节点名排序的邻接表，并计算每个节点的入度。
所有零入度节点构成初始候选集。处理节点 `u` 时，对每条边 `u -> v`
执行：

```text
layer[v] = max(layer[v], layer[u] + 1)
indegree[v] -= 1
```

当 `indegree[v]` 降为零时，`v` 可继续处理。扫描结束后：

- 所有节点均已释放：图无环，层号即从源点出发的最长路径长度。
- 仍有正入度节点：图有环，这些节点构成 `cycle_nodes()` 返回的
  “卡住节点集”，其中可能包含被环阻塞的下游节点。
- `layers()` 遇到卡住节点时抛出公开的 `CycleError(ValueError)`，
  不返回不完整布局。

单次分析的时间复杂度为 `O(V + E)`，空间复杂度为 `O(V + E)`。

### 1.5 全序枚举

枚举算法把 Kahn 算法中“从零入度候选选择一个节点”的动作扩展为搜索树：
每个候选节点对应一条分支。为避免递归深度限制，搜索使用显式栈。

每个栈帧保存当前候选元组、下一个候选下标，以及进入该层时选择的节点。
一次状态转移包括：

1. 按字典序选择一个候选节点并加入当前路径。
2. 降低所有后继节点的入度。
3. 将新释放的节点并入下一层候选集并排序。
4. 路径覆盖全部节点时输出一份列表副本。
5. 分支结束时弹出栈帧，恢复后继入度和路径。

按字典序深度优先展开前缀树，使 `iter_topo_orders()` 的输出顺序稳定。
`max_count` 在达到指定结果数后立即终止搜索。环图最终会在路径未完整时
耗尽候选，因此不产生结果。

设合法拓扑序数量为 `T`。输出本身已有 `Theta(T * V)` 的大小，所以全部
枚举不可能对任意大图保持多项式时间。

### 1.6 仅计数模式

`count_orders()` 复用同一显式栈状态机，但叶节点只将计数器加一，不复制、
保存或返回完整序列。它降低了结果存储开销，但仍需访问搜索树的每个叶子。

精确统计拓扑序等价于统计偏序的线性扩展，一般情形为 `#P-complete`。
因此“极速模式”表示避免构造结果列表，不表示任意 30/60 节点图都能快速
完成。界面层仍需对高分支图提供截断或用户提示。

参考资料：

- A. B. Kahn, *Topological sorting of large networks*,
  DOI: <https://doi.org/10.1145/368996.369025>
- G. Brightwell and P. Winkler, *Counting Linear Extensions is
  #P-Complete*, DOI: <https://doi.org/10.1145/103418.103441>

## 2. 渲染场景（scene/）——T4 撰稿（本章定稿稿）

> 任务 T4（issue #5）。设计取舍见
> [2026-09-19-T4-渲染场景设计](https://github.com/STU-MS/TopoSort/blob/master/evidence/decisions/2026-09-19-T4-%E6%B8%B2%E6%9F%93%E5%9C%BA%E6%99%AF%E8%AE%BE%E8%AE%A1.md)。

### 2.1 设计目标与约束

渲染层是「算法」与「观众」之间的投影：它**只消费** `layers` 与 `StepEvent`，
**禁止 import `app.models` 的算法函数**（契约 §5）。这样算法层可以独立测试，
渲染层也可以被脚本化的假事件序列驱动，从而可自动化断言。

| 约束 | 落地方式 |
|---|---|
| 只认事件、不懂算法 | 只 import `app.events.protocol` 的事件类型与 `layers` 字典 |
| 视觉状态可被自动断言 | 对外暴露 `node_state(node)`，返回稳定字符串 |
| 动画时长有界、可断言 | 时长常量集中在 `Effects`，上界 1000 ms |
| PNG 导出非空 | `GraphBoard.export_png()` / `CandidatePool.export_png()` |
| 三端通用 | 无平台专属调用 |

### 2.2 画布布局决策

候选池、分层图、泳道的相对位置有三个选项，最终选择 **A：候选池顶部、分层图居中、泳道底部**：

| 选项 | 取舍 |
|---|---|
| **A（采纳）** | 阅读顺序清晰（先看候选、再看图、再看分支），主图不被泳道遮挡，便于课堂截图 |
| B（候选池左侧） | 主画布更宽，但阅读动线被切断 |
| C（泳道叠加在图下方） | 会遮挡主图 |

### 2.4 渲染技术选型

| 选项 | 取舍 |
|---|---|
| **`GraphBoard(QGraphicsView)`（采纳）** | 复用 Qt 的场景图、平移缩放、PNG 导出能力，自研成本最低 |
| `QWidget + QPainter` 自绘 | 需自行实现平移缩放与命中测试，收益为零 |
| 逻辑包装器与外部 `QGraphicsView` 分离 | 多一层间接，无实际收益 |

### 2.5 视觉状态机与配色

状态机：`idle →（Enqueue）ready →（Consume）ghost`；异常态 `stuck`。

配色采用**高对比**方案（而非低饱和克制方案）：课堂投影与截图环境下低饱和难以分辨状态差异。

| 状态 | 填充色 | 描边色 | 语义 |
|---|---|---|---|
| `idle` | `#42516a` | `#9aabc4` | 待命 |
| `ready` | `#e4b94f` | `#ffe7a0` | 已进入候选池 |
| `active` | `#2c9de0` | `#8bd4ff` | 本拍被选中（脉冲） |
| `ghost` | `#657184` | `#aab4c3` | 已被消费 |
| `stuck` | `#e55353` | `#ffb0b0` | 环或环下游，被卡住 |

**一个精确性细节**：`node_state()` 对外只返回 `"idle" | "ready" | "ghost" | "stuck"`
四种——`active` 是 `Consume` 瞬间播放脉冲动画时的**瞬时视觉样式**，不是对外可查询的
稳定状态。测试因此断言稳定状态，不依赖动画中间帧（否则测试会因时序而抖动）。

### 2.6 动画与「保留过程轨迹」的设计取舍

**ghost 行为**有两个选项：

| 选项 | 取舍 |
|---|---|
| 消费后完全隐藏 | 画面干净，但丢失「哪些节点已被处理」的过程信息 |
| **消费后保留原位并半透明显示（采纳）** | 保留排序过程轨迹，观众能看出消点顺序；相关边同步淡化 |

采纳后者：本产品的核心价值是**展示过程**，而不是只展示结果。

时长常量集中在 `Effects`，上界 1000 ms（契约要求）：

```python
GHOST_MS = 300      # 节点渐隐为幽灵
PULSE_MS = 250      # active 脉冲
EDGE_DIM_MS = 200   # 边随节点消耗而淡化
```

**`Consume` 的复合语义**：逻辑状态**立即**变为 `ghost`（保证契约测试确定、不依赖动画），
同时播放 active 脉冲与渐隐动画（保证观感）——即「逻辑状态即时、视觉表现渐进」。

## 3. 事件引擎（events/）——T3 撰稿（本章定稿稿）

### 3.1 模块定位与文件结构

事件引擎是算法与动画之间的解耦层：把 Kahn 步进过程翻译成六类 StepEvent，
把"逐条演示"调度成"多泳道伪并发播放"。**零 Qt 依赖**，只读
`Graph.nodes / Graph.edges` 两个数据字段，Kahn 步进自研。

| 文件 | 职责 |
|---|---|
| protocol.py | 六类事件 dataclass 唯一定义 + `event_to_dict`（golden 序列化口径） |
| player.py | 步进内核 `_Kernel` / `_Branch` + 公共门面 `TopoPlayer` |
| timeline.py | 调度层 `Timeline`：泳道、拍、暂停/单步/调速 |

### 3.2 核心数据结构

```
_Branch（一条分支 = 一个部分拓扑序的 Kahn 状态快照）
    bid       int             分支标识（Fork 递增分配）
    indeg     dict[str,int]   各节点剩余入度（分支私有副本）
    frontier  set[str]        当前候选（入度已降为 0）
    enqueued  set[str]        本分支已发过 Enqueue 的节点（候选池去重）
    order     list[str]       已消费序列
    bound     str|None        Fork 绑定的首步备选（首步消费后清空）
    pending_visual bool       后台步进过、池尚未对观众补发

_Kernel（显式分支工作队列）
    _branches dict[int,_Branch]  按 branch_id 索引的活跃分支
    _succs    dict[str,list[str]] 邻接表（全分支共享，只读）
    completed list[tuple]        已完成的拓扑序
    _stuck_union set[str]        各分支卡住节点并集（→ CycleFound）
    capped    bool               max_completes 截断触顶
```

### 3.3 步进算法（`step_branch(bid, visual)`，一步 = 拿一个节点）

1. frontier 空：有剩余节点 → `DeadEnd(branch, 剩余全体)`（剩余节点此刻必然
   全部入度≥1，即环或环下游）；无剩余（空图）→ `Complete((), …)`。
2. frontier 非空，事件顺序固定为：
   `Enqueue*(首次进池节点, 字典序) → Consume(选中节点) → Fork*(k-1) → Enqueue*(本步解锁后继, 字典序) → Complete?(若消费完最后节点)`
3. 选中节点：bound 优先（Fork 子分支首步必须吃绑定备选，且**不再分叉**——
   该步全部备选已由亲代延续与兄弟分支覆盖，再分叉会重复枚举）；否则字典序最小。
4. 分叉：候选 k≥2 且非首步绑定 → 消费前快照状态，为其余 k-1 个备选各克隆
   一条新分支（`Fork(原分支, 新id, 原分支所选)`），branch_id 单调递增。

### 3.4 调度层（`Timeline`）

- **逐拍交错**：`iter_events()` = 无限泳道 Timeline 逐 tick 拼接（同一内核
  两种口径，golden 可互验，测试已锁定）。
- **拍首快照**：每拍只推进拍首已活跃的分支（按 branch_id 升序，前台后台
  交错各一步）；本拍新生/晋升的分支下一拍才推进。
- **拍末补位**：拍末把活跃分支按 id 升序取前 `lane_limit` 条入泳道（出生、
  晋升、释放统一按此规则，天然保证泳道分支不降级）；新入道且后台步进过的
  分支补发 Enqueue，拼在本拍事件末尾。
- **后台分支**：`step_branch(bid, visual=False)` 状态照常推进，仅 Complete
  照发；计数与结果不受泳道限制影响。
- **终止**：全部分支终止（或达 max_completes 截断）→ `CycleFound`（若有）
  拼最后一拍末尾，置 `finished`。

### 3.5 状态机（防御式边界，全表有测试覆盖）

| 调用 \ 状态 | running | paused | finished |
|---|---|---|---|
| tick() | 推进一拍 | 返回 [] | 返回 [] |
| step_once() | 自动暂停后走一拍 | 走一拍，保持 paused | 返回 [] |
| pause() | → paused | 幂等 | 幂等 |
| resume() | 幂等 | → running | 幂等 |
| set_speed(ms) | 生效（下限钳制 max(1, ms)） | 生效 | 生效 |

### 3.6 确定性保证

- 一切集合遍历/事件发射一律 `sorted()` 字典序——抵御 `PYTHONHASHSEED`
  跨进程随机化（已在三种种子下与 golden 逐项比对验证）。
- `order` 用 tuple、`stuck_nodes` 用 frozenset（可哈希、可比、内容序稳定）。
- golden 序列化口径唯一：`event_to_dict`（frozenset→升序 list，tuple→list）。

### 3.7 规模防护

`TopoPlayer(graph, max_completes=None)` / `Timeline(..., max_completes=None)`：
累计 Complete 达上限即收工、不再发任何事件。分支数 = 完整序数（每条序对应
一条分支路径），复杂度与回溯枚举同阶；阶乘爆炸用例（T9）依赖本参数截断。

另设**分叉前置保险丝**：Fork 前检查"已完成数 + 活跃分支数 ≥ max_completes
即不再开新分支"。原因：逐拍交错下首条分支需 n 步才产出首个 Complete，宽并
行图（多独立起点）此前分支已按组合数爆炸（实测 30 节点双链 26s 零产出）；
而每条活跃分支至多产出 1 个 Complete，故该上界与 max_completes 语义自洽。
不影响默认路径（cap=None）与既有事件语义，golden 逐字节不变
（设计留档：定案 §9 v4）。

### 4.5 信号槽接线表

界面层用信号槽解耦"控件事件"与"业务动作"，由 `MainWindow._build_ui()` 统一接线：

| 信号 | 槽 | 动作 |
|---|---|---|
| `ControlBar.start_clicked` | `click_start` | 启动全链路 |
| `ControlBar.pause_toggled(bool)` | `_on_pause` | 暂停/恢复时间线，并停/启 QTimer |
| `ControlBar.step_clicked` | `_on_step` | 单步推进一拍（调 `Timeline.step_once`） |
| `ControlBar.finish_clicked` | `_on_finish` | 循环 tick 至时间线 finished（上限 10000 拍，防死循环） |
| `ControlBar.speed_changed(int)` | `_on_speed` | 改 QTimer 间隔并同步 `Timeline.set_speed` |
| `InputPanel.open_requested` / `save_requested` | `_on_open` / `_on_save` | 弹文件对话框后走 `load_from` / `save_to` |
| `ResultsPanel.export_requested` | `_on_export` | 结果导出为 txt |

**动画驱动**：`QTimer` 按"每拍毫秒"触发 `_on_tick`，每拍向 `Timeline.tick()` 取一批
`StepEvent`，交给泳道与画布消费。界面**不自己计算排序**，只消费事件流——这正是事件层
存在的意义；也保证"过程可复现"这一契约（界面不引入任何随机性）。

### 4.6 降级设计（依赖模块未就绪时的行为）

> **现状**：T2 / T3 / T4 已于 2026-09-19～20 合并，本节所述分支**当前不会被触发**。
> 保留它们属于防御性设计（见下方"代价与收益"），T6 联调时决定是否清理。

界面层在调用算法/事件/渲染三个模块的**每个调用点**捕获 `NotImplementedError`，
转为状态行提示，界面不崩溃：

| 失败点 | 提示文案 | 界面表现 |
|---|---|---|
| `parse()` | 算法内核（models 模块）尚未完成，无法解析输入 | 输入区保留，结果流空，状态行红字 |
| `iter_topo_orders()` | 算法内核（models 模块）尚未完成，无法枚举拓扑序 | 同上 |
| `Timeline.tick()` | 事件引擎（events 模块）尚未完成，动画已停止（结果流不受影响） | 结果流照常显示，动画停 |
| `GraphBoard(...)` | 图画板：渲染模块（scene 模块）尚未完成 | 画布区显示占位文字 |

> 文案中**刻意不含版本号数字**（如 "T2"）：[`test_ui.py`](https://github.com/STU-MS/TopoSort/blob/master/app/tests/test_ui.py) 用 `"2" in error_text()`
> 断言行号，文案里出现数字 2 会让该用例在模块未完成时**假绿**——测试因错误的原因
> 通过比红着更危险。

**代价与收益**：这套 try/except 在三个模块合并后即成为惰性分支，但它换来了"界面壳可
独立开发与验收"，且删除成本极低（每个模块可逐条清理）。

### 4.7 错误呈现设计

契约要求呈现两类错误：解析错误（含行号）与发现环。

- **形式**：底部状态行横幅（错误时红底红字加粗），不使用模态 `QMessageBox`。
- **理由**：`QMessageBox.exec()` 会阻塞事件循环，自动化测试与截图脚本都会卡死；
  横幅同样满足契约"对话框或状态栏"二者之一，且可截图、可断言。
- **文案格式**：
  - 解析错误：`解析错误：第 N 行解析失败：<原因>（原文：'...'）`——直接复用
    `ParseError.__str__`，不另行格式化，保证与算法层报错口径一致。
  - 环：`检测到环：{A、B} 相互依赖，不存在拓扑序`——节点集取自 `Graph.cycle_nodes()`
    排序后拼接，便于回查是哪几个约束互相矛盾。

### 4.8 泳道与结果流的实现要点

- **泳道**（[`lanes.py`](https://github.com/STU-MS/TopoSort/blob/master/app/ui/lanes.py)）：`branch_id → _LaneRow` 字典；每条泳道维护 `consumed` 节点
  列表与 `state`（idle/ready/active/fork/done/stuck），由 `_LaneRow._refresh()` 统一
  渲染，避免状态散落。超过泳道上限（默认 8，取自契约）的分支**不建行**，仅累计计数
  并显示溢出提示——与 T3 时间线契约"溢出分支不展示但 Complete 照发"一致。
- **结果流**（[`results.py`](https://github.com/STU-MS/TopoSort/blob/master/app/ui/results.py)）：内部保存 `list[list[str]]`，控件文本由它生成（形如
  `1. A B C D E`）。对外给的是**序列列表**而非控件文本，避免把展示格式混进数据。
  导出为"一行一条序、空格分隔"，与契约一致。
- **结果上限**：`MAX_ORDERS = 2000`。全序枚举在稠密分叉图上呈阶乘增长，界面必须设
  上限防止卡死；上限经 `iter_topo_orders(max_count=...)` 由算法层截断（与 §1.6
  "极速模式"、T3 §3.7 规模防护同一考虑）。

### 4.9 跨平台处理

- 文件读写：`Path.write_text(..., encoding="utf-8", newline="")`、
  `Path.read_text(encoding="utf-8")`。写入端固定不转换换行，读取端走通用换行，
  保证"本程序存的文件往返一致、外部文件也能正确读入"。
- 无平台专属调用；无硬编码路径分隔符。
- 高 DPI：使用 Qt 默认缩放策略，窗口默认 1280×800。

### 5.1 集成联调：接线与桩替换

四模块并行开发期间，`scene` 与 `ui` 曾使用**桩事件源**以便独立验收。T6 的工作是把桩
替换为真实事件引擎，并打通全链路：

```
用户输入 → parse() → Graph ─┬→ layers() ────────────→ GraphBoard 静态分层布局
                            └→ TopoPlayer → Timeline ─→ 每拍事件列表
                                                              │
                          ┌───────────────────────────────────┤
                          ↓                                   ↓
                GraphBoard.apply_event()            CandidatePool.set_ready()
                LanesPanel 泳道轨迹                  /on_consume()
                          │
                          ↓
                Complete 累积 → ResultsPanel → 导出 txt
```

**界面不自己计算排序，只消费事件流**——这既是事件层存在的意义，也保证「过程可复现」
（界面不引入任何随机性）。

### 5.2 打包：三端一致入口

[`tools/build.py`](https://github.com/STU-MS/TopoSort/blob/master/tools/build.py) 是**三端唯一的打包入口**，把平台差异全部封装在脚本内部，
CI 三平台各自执行**同一条命令**：

```bash
uv run python tools/build.py --smoke
```

| 平台差异 | 处理方式 |
|---|---|
| 窗口模式 | 统一 `--windowed`（无控制台） |
| 产物名 | 固定 `--name TopoSort`（此前 CI 裸命令产出 `main.exe`，已修正） |
| 打包模式 | **macOS 用 onedir、其余用 onefile**（见 5.3） |
| 体积优化 | `--strip` 仅 Linux 默认开启（PyInstaller 官方标注 Windows 不推荐） |
| macOS 打包 | `.app` 用 `ditto` 打 zip（保留符号链接，见 5.4） |

### 5.3 关键决策：macOS 必须用 onedir

PyInstaller 6.22 源码明示（`PyInstaller/building/osx.py:33`）：

> Onefile mode in combination with macOS .app bundles (windowed mode) don't make sense
> (a .app bundle can not be a single file) and clashes with macOS's security.
> Please migrate to onedir mode. **This will become an error in v7.0.**

因此 [`tools/build.py`](https://github.com/STU-MS/TopoSort/blob/master/tools/build.py) 新增 `--mode`，默认 **macOS=onedir、Linux/Windows=onefile**。
`BUNDLE.assemble()` 用 `shutil.copyfile` 把依赖拷进 `Contents/Frameworks`，
故 `.app` 是自包含的，**只打包 `.app` 即可分发**。

附带收益：macOS 版没有 onefile 的解压步骤，**启动比 Windows 版快**。

### 5.4 关键决策：用 ditto 打 macOS zip

`.app` 内含 **103 个符号链接**（Qt framework 的 `Versions/Current → A` 等）。
Python 标准库 `zipfile` **不保留符号链接**，用它打包会产出缺 103 个链接的坏包。
`ditto -c -k --sequesterRsrc --keepParent` 是 macOS 自带工具，能正确保留链接与权限，
且不引入新依赖。

### 5.5 体积优化实测

| 配置 | 字节 | 结论 |
|---|---|---|
| 基线（无优化） | 72,257,448 | 68.9 MB |
| 仅开 `--exclude-module`（51 项 Qt + 13 项 Python） | 72,258,160 | **收益 ≈ 0（差 +712 B 属噪声）** |
| 排除 + `--strip` | **71,363,616** | **−894,544 B，唯一有效杠杆** |

排除清单收益为零的原因：PyInstaller 的 PySide6 hook 按「被 import 的 Qt 模块」收集依赖，
`app/` 只 import 了 `QtCore/QtGui/QtWidgets`，未 import 的模块本来就不会进包。

**Qt 插件裁剪已评估后否决**：需写自定义 hook 覆盖 `hook-PySide6.QtGui/QtWidgets`，
该 hook 会同时作用于 Windows 与 macOS，而本机只能验证 Linux，风险收益不匹配，转为待办。

### 5.6 空目录启动冒烟

`tools/build.py --smoke` 把产物**单独拷进临时空目录**，以白名单环境变量启动
（只给 `PATH` / `QT_QPA_PLATFORM=offscreen` / `LANG`，剥离 `PYTHONPATH`、`PYTHONHOME`、
`VIRTUAL_ENV`、`LD_LIBRARY_PATH`），判据两条：

1. 进程启动后至少存活 10 s 不退出；
2. 这 10 s 内 stderr 未出现 `Traceback` / `ModuleNotFoundError` /
   `cannot open shared object file` / `could not load the Qt platform plugin` 等失败标记。

**刻意不在 `app/` 代码里加自检开关**——交付物不该埋「自动退出」后门。因此判据是
「存活 + 无异常」而非「自证渲染完成」，此局限如实记录。

### 5.7 发布流水线

[`.github/workflows/release.yml`](https://github.com/STU-MS/TopoSort/blob/master/.github/workflows/release.yml)：`push: tags: ['v*']` 触发，三平台矩阵各自
构建 + 跑全量测试 + 冒烟 + 计算 SHA256，随后由 `release` job 汇总发布。

- **不引入第三方 Action**：发布用 runner 自带的 `gh` CLI（`GH_REPO` 显式指定，
