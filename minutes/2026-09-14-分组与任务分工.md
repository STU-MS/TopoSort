## 会议内容

1. **任务布置宣讲**。组长 HandyWote 宣读老师任务书（`docs/assignment.doc`）要点：非网页 GUI；输入若干 `<a,b>` 有向关系；渲染有向图；输出尽可能多的拓扑序；结果与图片可导出、文本存储；须做环检测；小组需按周开会并留会议记录，最终验收检查会议记录。当场把作业文件与老师模板（`docs/meeting-minutes-template.doc`、`report-template.doc`）提交入库（提交：`docs: add assignment and templates`）。

2. **分组与角色分工**。本组定为**第一组**，共 5 人，按仓库模块单文件单一职责划分主责：
   - **HandyWote（组长）**：项目规范与留档体系、T1 骨架/CI/契约、T7 打包发布、可行性研究报告（01），并统筹进度。
   - **Asukadaisiki**：`app/models/`（parser / graph / enumerator，即 T2 算法内核）。
   - **xiaoliei**：`app/events/`（protocol / player / timeline，即 T3 事件引擎）。
   - **HanXuXie**：`app/scene/`（board / effects / pool，即 T4 渲染场景）。
   - **Frieda-Feng**：`app/ui/`（main_window / input_panel / control_bar / lanes / results，即 T5 界面壳）。
   文档分工约定「谁开发谁写自己章节」，开发量大者文档量对冲，组长只写 01 可行性并统稿（后续 09-15 决策文档 `2026-09-15-任务拆分总表.md` 与提交 `docs: T8文档分工细化` 固化本口径）。

3. **技术选型初步讨论**。产品目标定为：单文件双击即跑、文件/手工双输入、计算过程动画（节点消耗、队列变化、分叉伪并发泳道）、调速/暂停/单步、结果与图片导出。组员提出候选技术栈，留待次日（09-15）就位开发机后实测对比后定案。

4. **留档纪律确认**。全体同意采用「决策 → Issue → 留档 evidence/decisions/」「完成可见功能 → 截图 evidence/screenshots/」「性能测试 → 追加 evidence/benchmarks.csv」「测试用例 → evidence/test-data/」四条习惯，并同意工程统一使用 uv 管理、算法必须自研（禁用现成排序库）。

5. **下周计划**。HandyWote 于 09-15 落定技术栈、工程规范与包骨架；其余四人先各自阅读任务书、熟悉自己模块的接口预期。
